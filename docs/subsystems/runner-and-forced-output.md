# Runner and forced-output boundary

Autopilot's child runner is split between a tiny npm wrapper and Rust Core-owned `agent-run` mode. Host code never chooses roles, modes, prompts, timeouts, runner paths, or result acceptance.

## Source map

| Concern | Source |
|---|---|
| Package-contained runner resolution | `src/resolve-core.ts` |
| Core command/spec construction | `drivers/src/runner/mod.rs` |
| Child runner validation and Pi JSONL handling | `drivers/src/runner/child.rs`, `drivers/src/runner/rpc.rs` |
| Checkpoint policy, Core admission, and Host broker | `data/checkpoint-policy.kdl`, `drivers/src/checkpoint/mod.rs`, `drivers/src/seam/mod.rs`, `src/child-control-broker.ts` |
| Terminal carrier acceptance | `drivers/src/seam/mod.rs` |

## Parent-to-child launch

1. `CoreTransport` resolves `process.execPath` and `bin/autopilot-agent-run.mjs` from the installed package and passes them to Core as transport facts. Its stdin error listener keeps active-run and arbitrary stream errors fatal; only `EPIPE`/`ERR_STREAM_DESTROYED` from the exact child after Host has entered its owned graceful-shutdown or closed state are contained.
2. Core writes a strict `autopilot.agent_run_spec.v5` for fresh `receipt_v1` execution, plus the rendered prompt and parent-selected generated terminal profile under deterministic `.pi/autopilot/<workstream>/...` paths. Historical source-free specifications remain reader-only and cannot launch Pi.
3. Core emits a `background_action` whose nested `bg_run` object is byte-exactly the public `pi-background-tasks@2.1.4` `run` payload. Every Autopilot-owned descriptor keeps `notifyOnCompletion: true` for durable operator notification and sets `triggerOnCompletion: false`, so completion is machine-consumed without waking the unrestricted parent model.
4. The central `control.bg-run-exact.v1` boundary rejects any package-issued descriptor that disables notification or enables parent-turn triggering, then requires the Host call to match every descriptor byte.
5. The Host forwards that object over `pi.events`; it does not rewrite fields, synthesize defaults, or call a Pi context method named `bg_run`. Generic background tasks outside Autopilot retain the background service's normal trigger behavior.
6. The background service durably publishes one terminal event. The Host correlates it to the exact action and sends `task-completed` directly to Core; replay/re-emission and watchdog actions use the same machine-only completion profile.
7. If correlation, Core transport, or next-effect application fails, the Host appends a bounded `rejection:host-terminal:` machine status before operator prose and rethrows. If machine-status publication itself fails, Host reports both failures through the non-triggering operator channel and still rethrows the original terminal error. It never infers success or continues after a possibly partial state transition.

## Child acceptance

`agent-run` validates all identity and route facts before launching Pi. It rejects stale carrier files, path symlinks, non-UTF-8 paths, role/mode drift, roster/provider/model/thinking drift, non-subscription/API-key routes, unknown tools, prompt digest mismatch, and deterministic path mismatch. Delivery context has one schema-versioned digest owner shared by issuance and child admission: the digest-bound assignment selects the V3 or V4 parser first, then that exact typed artifact supplies the version-specific context fields. One fallible role-typed runner authority owns delivery identity: `implementer` and `fixer-integrator` use `action-<workstream>-<lane>` / `assignment-<workstream>-<lane>`, while `recovery-engineer` uses `action-recovery-assignment-<workstream>-<lane>-a<attempt>` / `recovery-assignment-<workstream>-<lane>-a<attempt>`. Unknown roles never inherit ordinary identity; every role requires a nonzero attempt, and Recovery Engineer has a currently enforced one-attempt package invariant: issuance rejects any package maximum other than one. Parent construction/issuance/re-read, child artifact ingress, and validation/delivery crash resume all rederive from this authority using durable workstream/lane/role/attempt bindings rather than parsing IDs. A Recovery Engineer identity is accepted only with a digest-bound `autopilot.recovery_directive.v1` whose phase, mode, diagnosis, original gate, configured one-attempt policy, and selected-attempt bound are complete; an ordinary assignment carrying that directive or a Recovery Engineer assignment lacking it fails before Pi.

The child Pi process uses a run-owned session directory with `--no-extensions` plus the one codegen-anchored child add-on, bounded stdout/stderr, a wall timeout, and no metered API-key environment variables. Every JSONL frame, including discarded message/tool/Bash updates and oversized unterminated input, is bounded while streaming before it can allocate beyond the generated 4 MiB hard ceiling; a complete valid final JSON object at EOF remains a valid frame. The terminal and stderr environment knobs default only when absent; malformed values fail before launch. They may lower their hard ceilings but cannot raise or disable them. The stderr reader counts total bytes, retains only a bounded tail for diagnosis, and terminates the child process group before rejecting an overflow. Child exit never implies stderr success: Core terminates pipe-retaining descendants and requires one complete reader result; timeout, channel loss, overflow, or read failure rejects the run and is latched against a later shutdown retry. Graceful shutdown always follows group SIGTERM with group SIGKILL even when the leader exits first, so a SIGTERM-ignoring descendant cannot remain. Before prompting, Core verifies the streamed and durable registration receipt, selected profile, exact active tools, add-on digest, and assignment binding.

Every model assignment terminates through one parent-selected generated tool profile. `tool_execution_end.result.details`, correlated to `message_end(toolResult)` by opaque call id, is authoritative; assistant terminal text, mixed tool batches, duplicate results, identity drift, and stale unconsumed carrier files fail loudly. For the retained direct-carrier path, a valid terminal is prepared in memory, but its carrier, tool audit, model-submission artifact, and `accepted` attempt event are not persisted until mandatory stderr completion and successful child shutdown. Fresh V5 instead receives Core's already-durable receipt through the private broker before the tool result; the runner still grants no assignment success until exact result correlation, protocol EOF, stderr completion, and process-group cleanup all succeed. Before sealing a fresh `planning.work-map.v2` carrier, the child applies the same strict map shape, atom-link, topology, and ownership semantics as final Core admission; a model-value rejection enters the existing bounded same-session repair path. Carrier/spec identity, authenticated recovery-subject comparison, and derived package authority remain strict parent authority and never become model repair. Planning carriers retain their planning boundary payload. Delivery uses its model-only v2 submission. New Validator issuance uses the closed v3 boundary: the model supplies only semantic verdicts, allowed source/diff citations, and findings; Core derives identity, coverage, exact receipts, canonical order, normalized verdict, and outcome from digest-bound authority. Durable already-issued v2 Validator bindings retain strict exact-echo admission and are never coerced. Same-session terminal continuation is recorded in the create-once attempt-event ledger; it never adds undeclared fields to a closed carrier, and a continued tool result follows the identical generated carrier parser as a first-turn result.

Fresh V5 checkpointing is a parent-controlled continuation boundary, not another completion path. Pi automatic compaction is commanded off before the first prompt and `autoCompactionEnabled == false` is identity-checked both at bootstrap and after each manual compaction. The Rust runner observes same-session context telemetry at tool/message/turn boundaries, emits at most one soft warning per epoch at the data-owned 75% arm threshold, and, for a policy-declared interruptible role, at the 85% checkpoint threshold requests the generated universal `autopilot_checkpoint` tool with the role's data-owned required handoff slots. A non-interruptible role reaching that boundary fails closed instead of receiving a checkpoint tool request. A clean settlement may receive another same-session prompt only with known usage below 85%; unknown usage fails closed. Neither provider-error prose nor automatic threshold/overflow compaction authorizes continuation.

Core validates the bounded `autopilot.agent-handoff.v1` tree, preserves bounded unknown top-level fields, rejects numeric unknown leaves outside the shared Rust/JavaScript canonical domain (they must be encoded as strings), hashes its Rust-canonical JSON bytes, and returns a UUIDv7 `autopilot.checkpoint_receipt.v1` bound to the exact run/revision/assignment/attempt/role/mode/session/profile/tool call. The runner requires the ACCEPT details to correlate to the current tool-result message by exact call id, tool name, non-error status, and canonical details. A checkpoint call must follow a checkpoint instruction dispatched in that same agent epoch; delayed telemetry cannot authorize it retroactively. Context observations retain an epoch high-water mark under reordered RPC responses, and retry-start agents receive any still-required instruction. Unknown `terminate:true` tools, ordinary work after a pending ACCEPT, and malformed or additional stdout through protocol EOF all fail loudly. The runner waits for `agent_settled` and requires Pi's exact `pendingMessageCount` to be zero; RPC `abort` is never treated as a queue-clearing fallback. It then create-once persists the canonical receipt under the run root with private directory/file modes: an assignment/session-scoped pending name is directory-fsynced, its complete bytes are file-fsynced, it is atomically renamed to the final UUID name, and that publication is directory-fsynced (including the newly created checkpoint-root entry in its parent). Only then does it manually compact the existing Pi process/session, requires the compact response to prove a nonempty summary/kept boundary and reduced token estimate, rechecks session/provider/model/thinking/auto-compaction/idle/empty-queue identity, and sends only a checkpoint-derived resume packet. That packet binds the Core receipt's run, attempt, role, mode, session, original prompt/context/boundary identity, parent-observed context percentage, and exact handoff without inventing a planning identity for an execution role. Compaction failure leaves the canonical receipt durable; identity or queued-message drift blocks resume. Each successful compaction begins a new unlimited checkpoint epoch without an attempt counter, replacement model, or original-prompt replay. Before the first Pi prompt, startup race-safely materializes the shared private checkpoint root and every contender fsyncs its run-root parent; checkpoint ACCEPT can therefore never be the operation that first exposes an undurable shared directory. Every final flat checkpoint entry is bounded, canonical, filename/UUID/handoff-digest checked, and bound to the run. A closed pending filename is authority for its run/assignment scope (not its mutable session identity), so an interrupted write blocks every attempted session of that assignment without contaminating a sibling assignment. If a pending entry disappears between enumeration and metadata because a sibling atomically published it, startup restarts the entire authority scan rather than failing or blindly skipping the replacement final receipt. Prior final authority for the exact assignment or session likewise requires an explicit future checkpoint-derived recovery path. The original session path is link-checked, but checkpoint storage is derived by canonicalizing only its already-validated parent rather than the replaceable session entry; that canonical run root is pinned in memory for the entire child lifecycle, and the path is rechecked immediately before Pi spawn plus before and after RPC directory creation. Checkpoint persistence consumes only that pinned store and never re-canonicalizes the mutable session path, so post-spawn relocation cannot redirect or hide authority.

Checkpoint ACCEPT terminates only the current prompt cycle. It creates no legacy carrier or accepted-attempt event and cannot validate, package, integrate, close, release, or terminalize an assignment. Generated receipt-backed submit ACCEPT remains the only successful assignment terminal; universal BLOCKED retains its required observation and whole-workstream shutdown semantics. Historical/source-free replay exposes neither universal control tool.

Delivery verification has two typed owners. `commands` are pre-package child evidence. Core projects each command to a deterministic package-owned id in `autopilot.delivery_assignment.v3`; delivery roles receive `autopilot_run_approved_command`, not general Bash, and can provide only that id. The pinned add-on resolves exact command bytes, unit, cwd, assignment digest, and closed effect/handling authority, executes through a hidden bounded shell backend with session-environment exposure disabled, and serializes execution with edit/write and `autopilot_set_executable`. Mutable authored-leaf authority includes one narrow executable-state operation: after an exact authorized regular file exists, a delivery worker may set it to Git mode `100755` or `100644`; protected Core leaves, symlinks, directories, and unapproved paths remain denied before effect. Planning-repair and read-only roles never receive this tool. Policy `autopilot.delivery_tool_policy.v4` snapshots the content/mode-sensitive exact approved-file set before and after every command. A persistent change to any declared delivery file—on command success or failure—produces only a failed ledger row and a loud tool error; invalid post-command topology receives a package-private failure-marker digest rather than losing the audit row. Commands therefore cannot receive success evidence for bootstrapping, authoring, copying, vendoring, regenerating, repairing, or changing executable state on declared delivery files. The child remains inference-free and does not spawn Git or recursively infer repository scope: Core independently inspects the complete Git state, rejects every undeclared changed path, and requires every command to have a success receipt on the final approved-file snapshot before packaging. It then mints package-commit-bound command evidence for the independent Validator. Legacy v2 requires an exact criterion receipt echo; v3 instead validates the exact criterion matrix as package authority and auto-binds those receipts without exposing receipt fields to model output. Exact-tip source records cover surviving approved files; approved deletions are separately bound as deleted paths and remain inspectable through the exact candidate diff. An explicit package-owned unchanged-recovery posture permits only a round-two no-defect candidate with an empty exact Git diff.

Planning and delivery share one exact file-authority invariant. Every `units[].files` value is a normalized repository-relative regular-file destination, including valid extensionless files; directory, ancestor/prefix, glob, reserved, and inferred-expansion authority is rejected. Missing parent directories are derived only from those enumerated leaf paths. An existing directory is never coerced into a file, and an unknown future leaf set is a planning context gap rather than permission to widen scope.

Planning also owns verification-time availability. At the instant a unit runs, its commands may depend only on base state, Core-materialized state, its own leaves, and leaves owned by declared transitive predecessors. A descendant owned by a successor cannot lend its parent-directory existence to an earlier unit. Compiler and Synthesizer keep early checks unit-local and put whole-package/topology checks on a final closure that depends on every producer; Reviewer blocks any mismatch, and redundant impossible early checks are deleted rather than repaired by widening file or command authority.

`package_checks` remain closed Core-owned obligations for V1. Fresh `planning.work-map.v2` never projects proofs into legacy `ApprovedUnit.package_checks`: `files` are exclusive implementation-owner leaves, while explicit `package_scope_files` is package/read closure only and never child write authority. With V2 proofs or bindings, exactly one final closure carries every proof, its package scope exactly equals the global owner-leaf set, and it transitively depends on every other unit. A vendoring unit still exclusively owns its destination/manifest in `files`; another final closure may only echo those leaves in package scope. Core persists the V2 image only with a separate external-digest binding that roots the exact source carrier, raw payload, atom registry, and any recovery subject; planning creates no repository inventory or commit/tree/status authority. After the lane worktree exists, Core reads only the approved exact origin leaves once, records their bytes, mode, and SHA-256 in the materialization baseline, writes and protects the destinations, and never reopens origins during replay or package proof. V4 package-state equality compares only Git-visible approved package leaves; ignored Core-private materialization intention/receipt files are instead required and validated through their independent canonical digest-bound replay before package establishment and again before acceptance. If either private artifact is missing or altered, replay rejects; if any private artifact unexpectedly becomes Git-visible, exact package-state equality rejects it as undeclared. Unbound image, binding, materialization, or receipt bytes are unreadable. V1 `package_checks` remain closed Core-owned obligations. A unit carrying one is mechanically a closure unit and must declare the complete union of all work-map files, so an integrated repair cannot require authority invented after planning. `clean-exact-package-tip` is proved only after an admitted succeeded submission by Core's exact commit/tree, base-ancestry, strictly clean worktree (including nonignored untracked residue), and changed-path equality checks. Package checks never become child shell. Every check declares unique in-range 1-based `criterion_ordinals`; Core emits a digest-bound package-check receipt only onto those criteria. Legacy v2 exact-echo admission requires each affected criterion to cite it; v3 keeps it out of model context/output and Core auto-binds it from the validated authority matrix. Missing or older assignment/audit fields fail closed rather than defaulting to child authority.

The child delivery policy records only unknown approved-command ids refused before execution in a bounded digest-only denial ledger. The ledger cannot be supplied by model parameters, carries `effected=false`, and saturates visibly after 32 entries. Edit/write/path/topology refusals are not relabeled repairable. Core revalidates both denial and execution ledgers against the pinned add-on, exact assignment, final source snapshot, and audit digests and separately inspects Git; a denied reference is therefore distinguishable from an effected mutation without trusting model prose.

Fresh subscription-backed child processes use the data-owned deterministic startup spread in `data/recovery.kdl`. The spread is derived from workstream plus planning ordinal or package lane identity, so planning and delivery/validation siblings in one wave occupy distinct bounded launch buckets instead of reading the OAuth credential store together. It does not inject credentials, use an API-key fallback, alter the route, retry model content, or apply to resumed sessions.

## Recovery Engineer

A semantically admitted model result can be wrong even when its general direction is correct. Autopilot therefore has one phase-bound `recovery-engineer` attempt before terminal escalation:

- A non-pass first plan review launches a fresh planning-repair assignment with the canonical work map, complete rejected-review carrier, accepted planning evidence, task authority, atom registry, and the same review criteria. The Recovery Engineer independently verifies the diagnosis and returns one complete work map through the generated `recovery-work-map.v1` terminal profile. Core mechanically requires nonempty diagnosis/action/preservation evidence, identical unit identity/order/scope/dependencies/links, and an exact declaration of affected units. `repaired` requires declared surgical changes; `no-defect` requires every unit to remain unchanged. Both return to the unchanged full-review gate once. Another non-pass is terminal.
- A blocked delivery classified `semantic-repairable`, a mechanically reconciled pre-effect unapproved-command denial, or a first-round forward validation with semantic blockers launches the same role in a source-repair mode inside the original lane worktree. The package-issued delivery assignment carries the role-typed recovery action/assignment identity plus a typed recovery directive containing the rejected carrier, findings, evidence, original gate, exact approved units, base/tree, and a one-attempt budget. The typed finding selects a phase-appropriate mode (`forward-critical`, `failed-test`, `closure-repair` for evidence gaps, or `conflict-resolution` for contract defects), and the directive binds that mode to the assignment. Its submission must carry one closed recovery disposition. `repaired` requires succeeded with actual changes; `no-defect` permits exact in-scope prior changes or a mechanically clean unchanged commit. Normal delivery admission, package commit derivation, and independent round-two validation remain unchanged. A blocked Recovery Engineer or blocked round-two validator is terminal.

Blocked delivery must classify its blocker as `semantic-repairable`, `requires-new-authority`, `infrastructure`, or `unsafe`, but the model-selected label is evidence rather than sole routing authority. Core computes a typed recovery assessment from the exact assignment/audit digests, denial ledger, base HEAD, and safe in-scope dirty paths. `requires-new-authority` may receive one diagnostic Recovery Engineer only when the audit proves at least one bounded unknown approved-command id was denied before effect, the ledger did not overflow, HEAD still equals the exact base, and nonempty dirty paths remain wholly inside approved files. Core does not package or accept that blocked work. The fresh Recovery Engineer must independently submit `repaired` or `no-defect`; only then may Core package and send it to the unchanged independent gate. Missing denial evidence, clean/no-change state, path-policy denial, out-of-scope residue, HEAD movement, stale snapshot/provenance, infrastructure, unsafe state, or exhaustion stays terminal. A genuine authority gap therefore remains `requires-new-authority` after the one bounded diagnosis and never receives widened authority. The role cannot widen unit scope, change task authority or independent tests/gates, self-certify, mask infrastructure/provider errors, or create a second recovery loop. It may correct a task-owned implementation test only when that file is already in the approved unit and evidence proves the test contradicts unchanged authority.

Delivery recovery is event-before-action. `agent:delivery-blocked` records the typed admission and a content-sensitive worktree snapshot digest before any spawn. Restart re-reads the bound carrier, assignment, audit, HEAD, paths, file contents, and executable-mode summary; all Git stdout/stderr used for that snapshot is bounded before allocation and overflow terminates the process group. Any mismatch rejects replay instead of adopting drift. Once the recovery binding exists, normal exact re-emission and terminal-consumption guards prevent duplicate attempts.

Fresh receipt-v1 V3 admission aggregates every independently knowable model shape/value mismatch into one canonical sorted in-memory `autopilot.validation_admission_diagnostic.v1` value. Ordinary rows have a stable code, real JSON pointer, criterion/finding identity, same-domain expected/actual arrays, missing/extra values, and duplicate counts. If bounded input produces more than 2048 rows, Core retains the complete pre-summary `mismatch_count`, keeps 2047 canonical rows, and adds one root-pointer count/digest summary binding every omitted row; model input never becomes fatal merely because its diagnostic is large. Long values are transformed and then re-sorted. Byte-ceiling compaction uses package-private summaries of each original full value set, so repeated compaction preserves the original count and SHA-256 instead of hashing an earlier summary representation. Rejected receipt-looking model strings become digest-only redactions before diagnostic JSON can enter a repair prompt.

A rejected fresh V3 diagnostic is never persisted or recorded as an attempt event: Core returns `RETRY`, and its generic `submit.value` repair diagnostic exposes only a bounded 256-byte value preview plus digest/count metadata rather than the complete canonical V3 JSON. Source records retain the exact commit/tree Git blob identity but bind their readable digest and line count to the bounded no-follow worktree bytes the model actually receives, so clean CRLF, encoding, or smudge-filter projections remain readable without confusing them for Git facts. The one diff record exposes its digest-bound readable `diff_path`. Context and evidence files are opened no-follow, checked as regular through the descriptor, and read through a `max + 1` streaming cap before hashing, so replacement or growth cannot force an unbounded allocation. Package-state Git stdout/stderr is drained concurrently through fixed byte ceilings; either stream's read error or overflow terminates the process group before rejection. If the Git leader exits while either pipe reader remains pending, Core also terminates the group before waiting, so a descendant cannot retain a pipe and bypass late failure handling. Core accepts duplicate-free model arrays in any order and derives canonical criterion/finding/citation order itself; both child and parent compare the admitted canonical submission, and the parent independently rebuilds and byte-compares the normalized verdict. The per-cycle RPC terminal budget resets for each bounded repair while cumulative diagnostics remain visible. Malformed shape or semantic value receives unlimited same-session `RETRY` without a value-attempt exhaustion counter. Package authority corruption is fatal; only an admitted semantic blocker may route to the one Recovery Engineer.

Planning provenance is immutable and unambiguous: the rejected synthesized map and recovered map use separate create-new projections, while each Recovery Engineer/reviewer binding records exactly one bounded subject carrier path and SHA-256. Recovery comparison and approved-plan promotion reread that exact carrier and reject digest drift; ordinal-two review receives only the recovered subject. Delivery and validation record a typed pending-recovery event before issuing the child. Restart folds that event, deterministically recreates or re-emits the same assignment, and never allocates ordinary replacement work across the recovery window.
